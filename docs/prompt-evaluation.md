# Gemma 分类提示词对比

v0.3.0 使用 **V2.1 评分标准**，保持 0–4 分、Gemma 4 E4B 与 V2 单次分类流程。原 V2 文件保留供对照，V3 多阶段流程未恢复。本版没有用户习惯自适应；版本记录见 [v0.3.0](../releases/v0.3.0.md)。

## V2.1：任务要求、评分边界与关键短板

新规则位于 [router-system-v2.1.txt](../src/cirno_route/resources/router-system-v2.1.txt)，由 `classifier.py` 的 `PROMPT_VERSION` 选择；审计元数据记录实际版本和哈希。旧文件 `router-system-v2.txt` 不变。Pi 重启或 `/reload` 后加载新后台；独立 Python/API 进程需重启。

- 先识别交付物、核心操作、实际难度及关键约束；不自行增加任务没有要求的能力。
- 4 分需要正向证据覆盖相当难度和全部关键要求；主要工作有依据、细节仍需有限外推时为 3 分。缺少实测不自动扣分，资料篇幅不作为能力依据。
- 核心操作明确不支持时要求 0 分，未知能力与缺少必要输入要求 null；相关辅助能力不能补偿核心短板。
- 简单任务允许并列满分；分数不混入价格、品牌或未使用的高级能力，证据可信度通过不确定性另行表达。

输出字段、0–4 范围、价格路由的 3 分达标门槛及每批一次推理均保持不变；没有增加内部多阶段模型调用。紧凑格式仍使用稳定候选排序，不截断任务或能力证据。

### 保留的失败与边界

- 原有固定回归仍有 1 项失败：未提供名称/访问条件的私有数据库实时事务任务未弃权。其他验证中，隐含缺少测量数据、未提供文件内容的请求也仍可能得到分数。
- 明确不支持证明、异步调度或并发一致性的候选仍可能得到 1–2 分，而非标准要求的 0 分；开放能力说明也仍可能被误判为明确不支持。没有以程序强改分数或调整预期掩盖这些失败。
- 只有 configured 证据时仍出现 low 不确定性：两版在最终 51 次合成请求的 151 条候选记录中分别为 39、24 条。提示词关于证据可信度的要求仍未被完全遵循，不确定性不是校准概率。
- 收紧标准后，有证据的评分也不保证实际回答遵循全部约束；更细的能力资料和实际任务评测仍是后续方向。本次没有将这些限制宣称为已解决。

108 项 Python、55 项 Node 自动化与 Ruff 检查通过。生产默认 V2.1 在紧凑及完整协议下的真实 Gemma 检查均成功，每次只有一次模型调用、候选齐全且偏好为空。临时评测脚本、输入、报告、日志和运行锁在测试结束后清理；仅在本页保留摘要，没有新增测试数据文件。

## 提示词设计

新版文件为 `src/cirno_route/resources/router-system-v2.txt`；原始 `router-system-v1.txt` 保留为对照。

- 根据交付物和实际操作区分编程、语言转换、创作、提取、计算证明、设计分析；`task_type` 和领域关键词不能覆盖正文。例如翻译 Python 文档不等于编程，从小说介绍提取字段不等于创作。
- 采用相同的绝对评分尺度，先判断明确不支持和资料不足，再评估支持程度；避免把候选擅长的辅助工作当成任务核心。
- 简单任务可以并列高分，不奖励任务用不到的复杂推理能力；质量分不混入费用、速度、模型品牌或输入顺序。
- 将配置声明与实测区分，缺少实测本身不是统一扣分或添加 `EVIDENCE_INSUFFICIENT` 的理由。
- 增加边界示例；保留原有候选 ID、证据引用、空偏好和 JSON 合同。

## 对比方法

固定用例在 `evals/prompt-cases/task-fit-v1.json`，共 8 个开发用例和 9 个独立验证用例。合成候选明确限定能力范围，用于检查是否根据操作评分；真实型号的候选卡片取自当时的配置快照，用于检查简单任务并列、复杂任务支持程度和资料缺失。未修改真实候选卡片，也未增加模型能力事实。

所有期望在首次推理前确定。开发阶段第一版较长的规则提示词只通过 5/8，出现信息提取与创作混淆，未启用。补充具体边界示例后通过 7/8，随后冻结提示词再运行验证集，没有根据验证结果调参。

新旧提示词使用同一已锁定 Gemma Q4_K_M、llama.cpp `b10516-b95502ba9`、上下文 8192、temperature=0、seed=42、thinking 关闭、最多 1536 输出 token。每个用例串行执行两个版本并交替先后顺序。两组使用相同输入、Schema、重试与校验机制。此次均为单次成对运行，没有多次抽样估计。

通过数表示满足用例中预先写定的比较/弃权期望，同时通过输出合同与空偏好检查；它不是供应商模型的真实任务成功率，也不表示提示词全部语义规则均已满足。顺序与名称变体来自已有验证任务，不是额外的独立任务分布。

### 已知未解决问题

- 缺少照片的身份识别、无法访问的实时私有数据库，两版本都没有正确弃权；v2 仍分别给出 3/3/3 和 3/4/2。这些是失败案例，不计通过。
- 候选倒序后，报错改写任务的合成数据候选从1变2；最高分写作候选仍为4，但精确分数不变性检查失败。
- 合成卡片已明确不支持某些核心操作，Gemma 仍有给1或2而非0的情况。新版更明确的评分尺度没有完全消除绝对分数校准问题。
- 虽然提示词要求仅有配置声明时至少为 medium，v2 的17个用例仍有5个包含 low（v1为12个）；本次没有通过改写模型结果掩盖这一点。`uncertainty` 不能视为经过校准的置信度。

因此本次启用 v2 的依据是有限固定测试上的改善，不是全部问题已解决。当时分类只展示评分，不承担自动选模或授权决策。后续提升需要更细的候选能力证据和独立任务测量，不能只靠扩大分差。

开发初稿、冻结开发集与验证集分别输出独立报告，包含全部分数、原因码、证据引用、提示词/输入/模型哈希、usage、耗时及失败检查。原始报告位于被 Git 忽略的 `.runtime/`，不随源码分发；可用下文命令生成自己的新报告。

```bash
.venv/bin/python scripts/evaluate-prompts.py --split dev --output .runtime/prompt-dev-new-run.json
```
