# Pi 多模型协作路由

`/superbakarouter` 让用户只和一个统筹模型对话。统筹根据项目现状拆任务，本地 Gemma 和价格策略决定每个工作包由哪个模型负责。统筹实际派发工作、收取报告，再在当前 Pi 会话中整合和验收。

```text
/bakaprice 均衡
/superbakarouter
制作一个书架网站。先约定图书 API，再分别实现后端和前端，最后整合。
```

| 命令 | 作用 |
| --- | --- |
| `/superbakarouter` 或 `/superbakarouter on` | 进入协作模式，从下一条普通输入开始选统筹 |
| `/superbakarouter status` | 查看模式、价格偏好，以及当前或最近一轮的统筹、分工、实际派发模型和汇报状态 |
| `/superbakarouter off` | 结束协作，停止在途派工。后续普通输入使用 Pi 当前模型 |
| `/bakarouter` | 切换为原有的单模型自动路由 |
| `/classify 任务` | 单独查看这项任务的候选评分和推荐模型 |

协作默认关闭，新会话或重载后需重新开启。它与单模型自动路由互斥，协作回合不命中或强化单模型习惯。进入协作模式不会主动调用执行 API。

## 统筹如何派工

1. 本地 Gemma 判断统筹、工具使用与整合所需的能力，程序按相应榜单分项和价格选出统筹，Pi 将当前会话交给它。简单任务可以由统筹独立完成。
2. 统筹按任务规模和依赖关系决定工作包数量，可以一次提交全部分工，也可以在同一轮继续追加。统筹用 `cirno_team_assign` 提交各部分的职责、交付物和验收要求。每个工作包复用同一十分制接口，返回工作包 ID 和分配到的模型。[榜单评分规则](benchmark-routing.md)
3. 统筹通过 `cirno_team_dispatch` 按 ID 派工，执行模型从这一步开始接收请求。例如，先取回规划角色的接口约定，再把约定交给前端和后端。独立工作包可以同批派发。执行者只收到自己的任务和统筹明确提供的资料。
4. 执行者通过 Pi 已配置的模型服务交回代码、补丁、分析或文稿。状态变为“已汇报”时，统筹就能核对这份成果。工作区的文件读写、命令执行、验收和最终交付都由统筹负责。

## 价格、文件保护与失败处理

- 统筹、执行者和备选模型共用本轮 `/bakaprice` 的偏好。“希望便宜”在能力达标的候选中优先选低价。“均衡”仅在能力差距小、价格节省明显时选便宜模型。“接受昂贵”优先任务质量，同分时选已知价格较高的候选。候选需要有能力依据才能入选。分数与价格相同时，优先分给承担工作较少的模型。同一模型也可以负责多项分工。各次 API 调用分别计费。
- 每次从 Pi 当前会话可用且已过冷却期的实体模型里选。分工时记录端点和 API 类型，派发前重新核对。普通对话显示角色和模型，各候选的分数可通过 `/classify` 查看。
- 配置了保护路径时，统筹和执行者只从已登记的本地或可信模型中选取。分工、派发、汇报都经过会话保护检查，执行请求使用 Pi 原有的认证和发送保护。[文件保护说明](file-privacy.md)
- 同批派发的工作包最多同时执行 **2 个**，其余自动排队。每个工作包最多调用执行模型 **2 次**。遇到可识别的临时服务错误（如 HTTP 503），路由器会按原价格偏好为该工作包选一个合格的备选。如果报告质量未达要求，统筹也可以给出反馈，要求原模型返工或重新选模。若备选不足，统筹会收到该工作包未完成的状态，其余已交回的成果仍可使用。
- 用户取消、关闭模式、手动换模或在协作期间修改价格偏好，会使在途分工失效。已经发给供应商的请求仍可能计费。统筹开始使用工具后，插件不会自动重放整轮任务，以免重复写文件或运行命令。

分工状态只保存在当前进程中；Pi 自身会按其会话设置记录工具输入和报告。不要把与该工作包无关的资料或凭据作为派发上下文。
