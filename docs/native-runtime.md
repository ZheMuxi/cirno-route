# 插件内置 node-llama-cpp 后端（试验）

v0.3.0 默认使用插件内置的 `node-llama-cpp` 原生后端，保留插件管理的 `llama-server` 供显式切换。后端切换不修改 Gemma 权重、V2.1 提示词、0–4 分制、候选分批、价格策略或用户习惯范围。

## 安装与启动

先完成 README 的基础安装与凭据配置，然后从仓库根目录执行：

```bash
./scripts/install-native-runtime.sh
./scripts/start-pi.sh
```

完整安装入口 `install-pi.sh` 已包含原生依赖安装；已有安装可以单独补装。`start-pi-native.sh` 也保留为明确选择原生后端的入口。启动参数透传，例如 `--model your-provider/your-model`。Pi 内继续使用 `/classify`、`/bakarouter` 和 `/bakaprice`。只分类时不执行回答模型，普通对话仍只显示实际回答模型。

退出 Pi 后运行 `./scripts/start-pi-llama.sh` 可切回原 `llama-server` 后端，也可使用 `CIRNO_LOCAL_BACKEND=llama-server ./scripts/start-pi.sh`。普通入口尊重已有环境变量中的显式选择；取消变量即可恢复原生默认。`CIRNO_RUNTIME_REUSE` 只控制旧后端是否复用外部服务，新后端始终加载自己的原生库。切换后端需要重新启动 Pi，`/reload` 不会更改启动时的环境变量。

## 内置方式

```text
Pi 扩展
  → Python 分类与校验 worker
    → 私有 Node worker（进程管道）
      → node-llama-cpp 原生库 → Gemma GGUF
```

原生依赖位于 `packages/pi-extension/native-runtime/node_modules/`，通过单独的 `package-lock.json` 锁定，不修改 Pi 的全局依赖或现有 `node_modules` 链接。固定 `node-llama-cpp 3.22.2`，其随包 llama.cpp 为 `v0.7.0`；旧后端继续使用已锁定的 `b10516-b95502ba9`。安装使用 npm 完整性校验；推理过程中禁止下载、编译或静默升级原生代码。

首次分类仍会检测现有模型缓存，缺少模型时沿用固定版本及 SHA-256 的下载器。原生包需先执行安装脚本；当前不在用户提交任务时自动运行 npm。依赖缺失会报告 `NATIVE_DEPENDENCY_MISSING`。只有当前平台存在可用预编译库时才加载，不静默转为源码编译。本轮主要验证 macOS Apple Silicon，其他平台尚未实测。

该后端不启动 `llama-server`、不创建本地推理 HTTP 端口。Python 仍负责原有能力研究、输入输出合同、提示词与分批协议；这不是去除 Python 的完全重写。联网能力查询和回答模型服务继续使用原有配置。

## 模型校验与生命周期

- 继续校验权重哈希、模型文件状态、上下文长度，并用真实生成检查系统提示词和 JSON 语法约束。
- 原生后端使用明确关闭 reasoning 的 Gemma 4 wrapper，锁定 wrapper 渲染、原生版本和适配器代码哈希；记录独立的 `.runtime/native-model-lock.json`，不覆盖旧模型锁。
- 沿用紧凑及完整两种输出协议。原生语法转换保留分数范围、固定数组长度和候选证据枚举，Python 再做语义校验。
- 每次请求创建独立逻辑会话，模型权重与上下文容器常驻，允许复用共同 token 前缀；上一任务不会作为对话历史加入下一任务。
- 生成前计算实际模板 token 数并预留输出空间；超限拒绝，不通过上下文滚动丢弃候选。
- 退出、取消或超时关闭所属 Node 进程；父管道关闭时释放原生库。推理库与 Pi 分进程运行，原生崩溃不会直接崩溃 Pi。
- 新后端失败时不会偷偷启动旧后端；Pi 原有的分类失败处理保持不变，普通自动路由可能继续使用当前回答模型。

`metadata.local_backend.mode` 标识 `node-llama-cpp`，`runtime_url` 为 null，记录实际 GPU 后端。两个运行时使用不同 llama.cpp 版本、模板封装和语法实现，即使权重与提示词相同也不保证评分完全一致。

## 验证口径

功能回归覆盖原生默认后端、旧后端显式选择、协议校验、超时清理及语法约束转换。真实测试复用固定任务与同一权重，单独记录准备时间和分类时间；固定样例通过不代表实际供应商选模准确率，也不能直接推断内存更省。

测试脚本、原始模型输出、临时锁和日志使用临时目录，完成后删除。测试摘要保留在本文；不上传权重、密钥、会话或模型缓存。

### 2026-10-28 本地实测

同一份 Gemma E4B Q4_K_M、V2.1 提示词、8192 上下文、temperature=0、seed=42，顺序执行旧后端和新后端。权重已在本地缓存，未刷新联网资料；以下为单次开发对照，不是统计显著的性能结论。

| 项目 | llama-server | node-llama-cpp |
| --- | --- | --- |
| 固定 17 个用例的结构与语义合同 | 17/17 | 17/17 |
| 同一套任务评分预期 | 16/17 | 16/17 |
| 四个任务重新分类评分一致 | 4/4 | 4/4 |
| 17 次紧凑分类平均耗时 | 2.76 秒 | 2.55 秒 |
| 准备耗时（已有权重与文件缓存） | 1.20 秒 | 4.50 秒 |
| 完整 JSON 协议示例分类 | 13.62 秒 | 16.05 秒 |

两者都有 `validation-unknown` 未按预期弃权，保留为已知问题。17 个用例中 16 个完整评分向量一致；`dev-code` 的数据类次要候选为旧后端 1、新后端 2，代码候选仍为 4，首选不变。所有分类均一次生成完成，没有格式重试。两种后端均在生成前拒绝超出 token 预算的输入，测试退出后所属模型进程消失。

真实 Pi 另外执行两次 `/classify`，读取实际可用目录，冻结历史能力资料以避免联网刷新：两次均保留 39 个候选，其中 12 个有资料、27 个未知，分 2 批；编程约 28.42 秒、写作约 25.27 秒（包含插件端准备开销），同一原生进程复用，没有调用回答模型，Pi 退出后完成进程清理。本轮没有执行新的自动选模回答测试，不将这些结果当作远端模型质量评估。

另外通过真实取消分类、父进程强制退出的生命周期测试，确认所属 Python/Node 进程均退出，并用系统端口检查确认原生 worker 没有监听 TCP 端口。111 项 Python、57 项 Node 回归、Ruff、脚本语法检查通过；安装入口也通过锁文件离线重装验证。

设为默认后的发布复验：不传入后端参数，17 个固定用例仍有 17 项输出合同通过、16 项评分预期通过；真实 Pi 使用 39 个候选、2 批完成编程分类，约 28.75 秒，元数据确认 `node-llama-cpp`，没有调用回答模型，退出后清理成功。显式旧后端也完成真实分类。临时脚本、模型锁和日志均已清理。
