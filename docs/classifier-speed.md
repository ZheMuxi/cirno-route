# 分类提速与显示

本页记录此前的分类传输、分批和 Pi 显示优化。继续使用已锁定的 Gemma 4 E4B Q4_K_M、8K 上下文、V2 评分规则与无思考模式。后续新增的价格选模与执行流程见 [自动路由](automatic-routing.md)，以下耗时和固定执行模型为提速阶段记录。

## 压缩方式

- `router-system-v2.txt` 原文不变。附加的 `src/cirno_route/resources/router-wire-compact-v1.txt` 仅约定紧凑输入/输出格式。
- 模型输入使用请求内短 ID，省略品牌、revision 等不参与 V2 评分的标识；程序保留原始映射及原始候选哈希。保留完整 task、requirements、capabilities、证据正文、来源类型、实测样本数和限制。
- 联网证据中完全相同的固定说明只发送一次，其他正文逐字保留；没有再调用模型二次摘要，没有按关键词删减能力维度。
- 模型每个候选输出 `[质量分, 不确定性, 证据编号列表, 原因码列表]`；程序还原公开合同、完整候选/证据 ID、空偏好和弃权状态。任何必需评分为 null 就弃权；未知型号仍保留在总结果中。
- JSON grammar 固定候选集合、字段类型及各自的证据编号；恢复后执行原有严格校验。格式错误仍最多修复一次，运行时身份仍在调用前后验证。
- 候选按稳定 ID 排序，任务保留在资料前部。默认每批最多 8 个，先检查字节预算，再由 llama.cpp 实际分词检查上下文；太大的批次二分重试，单候选仍超限则明确报错，绝不静默丢候选或截断。

分类一直使用全新消息列表：固定规则 + 当前任务/资料，不带上次对话或分类结果。Gemma 进程保持加载以复用权重和公共前缀缓存；这不等于把上次聊天送入本次分类。每次销毁进程会增加下一次加载耗时。

## 配置与本地回退

项目 `config.json`：

```json
{"compact_protocol": true, "max_input_bytes": 30000}
```

`config/pi-classifier.json`：

```json
{"batch_size": 8, "batch_max_bytes": 28000}
```

这几个字段是现有配置中的字段，修改时保留其他设置。要恢复提速前的路径，将它们分别改成 `false`、`10000`、`3`、`9500`，然后重启 Pi 或 `/reload`。Python `Settings` 的默认值仍为旧协议，以保持未使用项目配置的调用方兼容。

## 显示规则

`/classify 任务` 展示全部候选分数和未知状态。`/bakarouter` 开启普通输入自动分类，但普通对话不显示或保存评分条目；`/bakarouter off` 关闭自动分类。两种状态都会在实际回答时提示 `本次回答模型：provider/model`。

显示值来自 assistant 消息，不是研究模型名、Gemma 分类器名或评分最高者。同一回答中的工具续传不重复提示相同模型；确实换模型时再次提示。网关的 provider/model 标识仍不能证明其内部没有别名映射。

## 复测

下面的可选测试只读取已有研究快照，使用同一台机器上的 Gemma 比较旧格式与紧凑格式，不会重新联网研究或执行用户任务。所有速度样本都真正进行推理，没有缓存分类答案。

```bash
.venv/bin/python scripts/benchmark-classifier.py \
  --catalog-report .runtime/pi-research-20261020T163227Z-report.json \
  --fixtures --output .runtime/compact-benchmark-new.json
```

输入报告及其引用的 `snapshots/` 文件必须存在；脚本会验证内容哈希。输出路径必须是新路径。测试结果保存在被 Git 忽略的 `.runtime/` 中。17 项合成用例衡量评分规则遵循情况，真实目录只检验速度、候选完整性和分数变化，不能充当各云模型的实测成功率。

额外使用 `--vary-tasks --repeats 5` 可轮换编程、写作、数学任务；`--modes compact` 只测紧凑路径。真实 Pi 的显示回归使用 `.venv/bin/python scripts/pi-display-smoke.py`，其中两轮普通算术对话会调用当前网关执行模型，能力缓存失效时也可能重新研究。

## 2026-10-21 本机结果

Gemma 权重、llama.cpp、8K 上下文、温度 0、种子 42 均保持原值。使用提速前报告引用的冻结资料：39 个候选全部保留，12 个有证据参与 Gemma 推理，27 个仍为未知；有证据候选从 4 批合并成 2 批。

| 同一编程任务对照 | 旧完整格式 | 最终紧凑格式 |
| --- | ---: | ---: |
| 该格式首次推理（不含进程启动、联网研究） | 66.49 秒 | 21.52 秒 |
| 同进程再次推理相同任务 | 48.97 秒 | 6.81 秒 |
| 累计 prompt tokens（含缓存部分） | 15,127 | 9,347 |
| 累计生成 tokens | 1,677 | 218 |

重复相同任务能命中更多 llama.cpp 前缀缓存，6.81 秒不是所有新任务的承诺。真实 Pi 顺序处理不同任务时，首次编程分类 **23.23 秒**，之后写作 **19.16 秒**、数学 **18.95 秒**，均返回 39 个候选。首次数值包含 Pi 后台及 Gemma 启动；这些测试使用有效的能力缓存，首次联网准备资料的额外时间不在以上比较内。

17 项语义对照：旧格式 **14/17**，最终紧凑格式 **15/17**，没有新增失败；候选换序用例通过。两项既有失败仍为“未提供照片但要求确切身份”和“未命名的私有数据库实时事务”，Gemma 未正确弃权。不能据此宣称解决所有 V2 缺资料问题。真实模型目录的编程评分有 4/12 项变化 1 级，两次各自重复结果一致；这些分数没有云模型实际执行真值，不能把一致性当准确率。

曾尝试将稳定候选资料放在任务之前以提高跨任务缓存命中，但出现新的翻译用例失败，因此已撤回；最终仍保留任务在前。没有为了缩短耗时而删除这项失败用例或更改预期。

完整同机对照：`.runtime/compact-benchmark-final.json`。被撤回的排列实验单独保留在 `.runtime/compact-benchmark-prefix.json`，其耗时不作为最终版本性能。自动化验证包括 Python 108 项、Node 36 项、Ruff 和 diff 检查。

最终真实 Pi 报告：`.runtime/pi-display-20261020T170838Z.report.json`。三次 `/classify` 均完整返回 39 行、39/39 缓存命中、2 批、无重分批。随后开启自动分类的一轮普通对话确实运行了 2 批分类，未输出评分卡；关闭后的一轮普通对话也没有评分卡。两轮都显示实际 `cirno-gateway/claude-sonnet-4-6`，均正常完成，无分类警告。
